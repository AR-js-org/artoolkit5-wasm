# Constants 0.4.0 Upgrade, Version Export and OIDC Release Implementation Plan

> **Historical document: superseded. Do not re-run it as written.** This plan was executed and
> shipped as 0.4.0, and the code that shipped differs from it in the ways listed under
> [Deviations from the plan](#deviations-from-the-plan) at the end. Two of them would break a
> release if the plan were followed literally: the release workflow must **not** set
> `registry-url` on `actions/setup-node` (it blocks the OIDC exchange), and `release-check`
> compares the `ARTOOLKIT5_WASM_VERSION` export of the built `dist/index.js` instead of searching
> it for the version string. The current procedure is in [`MAINTAINERS.md`](../../../MAINTAINERS.md)
> and the workflow is `.github/workflows/release.yml`.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move `@ar-js-org/artoolkit5-constants` to 0.4.0 (clearing the GPL-declared 0.3.0 pin), make the package report/export its own version, and give the repo a release workflow that publishes to npm through OIDC Trusted Publishing with provenance.

**Architecture:** Three small PRs against `dev` (Task 1 dependency + version export, Task 2 release workflow + a testable `scripts/release-check.mjs`, Task 3 script fixes), then a release runbook (Task 4) that opens the `dev` → `main` release PR, backfills the missing `v0.3.0` tag and cuts 0.4.0. The release workflow is a port of the one in `AR-js-org/artoolkit5-constants` (`.github/workflows/release.yml`), adapted to this repo: no Emscripten container job, `v`-prefixed tags, and a `dist/` sync check limited to the wrapper outputs.

**Tech Stack:** Node 24 / npm ≥ 11.5.1, GitHub Actions, Vite 8, TypeScript 7, `node:test`, Docker (`emscripten/emsdk:4.0.17`, only for `build:wasm`).

**Spec:** No design doc. Sources are open issues [#31](https://github.com/AR-js-org/artoolkit5-wasm/issues/31), [#30](https://github.com/AR-js-org/artoolkit5-wasm/issues/30), [#27](https://github.com/AR-js-org/artoolkit5-wasm/issues/27), the user's 2026-10-03 request (constants upgrade; confirm the release script supports OIDC), and the reference workflow above.

## Findings that shaped this plan

- **There is no release script or workflow here.** `.github/workflows/` holds only `ci.yml`; `package.json` has no release script. `@ar-js-org/artoolkit5-wasm@0.3.0` was published by hand: npm shows no attestations for it, and `git tag` stops at `v0.2.0` (no `v0.3.0` tag, no GitHub Release). Its npm `gitHead` is `aba7373`.
- **Provenance would fail as the repo stands.** `package.json` says `https://github.com/ar-js-org/artoolkit5-wasm.git` (lowercase org, no `git+`); the repo is `AR-js-org/artoolkit5-wasm`. `publishConfig` is absent.
- **The upgrade target is 0.4.0, not 0.3.1.** #31 was written against 0.3.1, but 0.4.0 was published today (2026-10-03). It is MIT, has attestations, and `export *`s two new names, `VERSION` and `ARTOOLKIT_CONSTANTS_VERSION`. `src/index.ts` does `export * from '@ar-js-org/artoolkit5-constants'` and spreads the constants into the frozen `constants` object, so after the upgrade this package would silently export the *constants* package's version as `VERSION`.
- **#30 is mostly already done.** `vite.config.ts` defines `__VERSION__` from `package.json`; the "hardcoded" `v0.3.0` in `dist/index.js` is that define resolved at build time. What is missing is a programmatic export and a guard against shipping a stale `dist/`.
- **#31's CI claim is stale.** `ci.yml` runs `rm -f package-lock.json && npm install`, so CI is not pinned to 0.3.0; the lockfile only matters for local builds and for any `npm ci` release job. It also means `npm ci` has never been exercised on Linux here (the removal exists to dodge a Rollup optional-dependency bug).
- Not planned now: #29 (low, blocked on global-ID markers), #24 (low, needs a contract decision), #19 and #20 (real but larger; #20's wasm non-reproducibility is why the release `dist/` check excludes the wasm), #16, #10, #9.

## Global Constraints

- Branch from `origin/dev`; every PR targets `dev` (decided by the owner on 2026-10-03; `dev` and `main` are currently identical). `main` receives `dev` only via the release PR (Task 4). Conventional Commits. End commits with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- Git tags are `v`-prefixed (`v0.1.1` … `v0.2.0`); keep that. The workflow input `version` is bare (`0.4.0`), the tag is `v0.4.0`.
- Release runs on Node 24 with npm ≥ 11.5.1; `.nvmrc` contains `24`.
- Actions are pinned by commit SHA with a version comment, as in `ci.yml`: `actions/checkout@df4cb1c069e1874edd31b4311f1884172cec0e10 # v6.0.3`, `actions/setup-node@48b55a011bda9f5d6aeb4c2d9c7362e8dae4041e # v6.4.0`.
- `dist/artoolkit5.js` and `dist/artoolkit5.wasm` must not appear in the diff of Tasks 1–3 or of the release PR (precedent: the 0.2.0 and 0.3.0 release commits). Only `npm run build:wrap` is run, never `build:wasm`.
- No `NPM_TOKEN` secret anywhere. The `release` job alone holds `id-token: write` and `contents: write`.
- The repository URL everywhere is `AR-js-org/artoolkit5-wasm` (exact case).

## Review Focus

1. A consumer importing `VERSION` from this package must get *this* package's version, not artoolkit5-constants'. (Task 1)
2. `npm ci` on Linux against the regenerated lockfile must succeed (Rollup/Rolldown optional native bindings), or the release job cannot install. (Task 2)
3. A release run where the version is on npm but no tag/Release exists must resume and create the Release rather than fail or republish. (Task 2)
4. A release dispatched from a non-`main` branch, with a version that is not plain stable semver (`v0.4.0`, `0.4.0-rc.1`, a multi-line string), or with a tag already pointing at another commit, must be refused before anything irreversible runs. (Task 2)
5. A release where `dist/index.js` still embeds the previous version (forgot `build:wrap`) must be refused. (Task 2)

## Deviations from the plan

What changed between this plan and the code that shipped in 0.4.0, and why. The ledger that
recorded these during execution was scratch and has been deleted; this is the surviving record.

**Process**
- Work was done in place on branches off `dev`, with no git worktree. Tasks 1 to 3 were stacked
  PRs; because the repository merges by rebase, each later PR was rebased onto `dev` (with
  `--force-with-lease`) after the one below it merged.

**Task 1 (constants 0.4.0, version export)**
- `"test"` is `node --test "test/*.test.mjs"`. The directory form `node --test test/` fails on Node 24.
- The fourth test checks `src/index.ts` for the destructuring instead of reading the runtime
  `constants` object: the committed wasm glue is built for `ENVIRONMENT=web` and cannot be
  instantiated in Node.

**Task 2 (release workflow)**
- `checkRelease` is **async** (`Promise<string[]>`) and imports `dist/index.js` to compare
  `ARTOOLKIT5_WASM_VERSION`. The planned text search for the quoted version would pass a stale
  `dist/` whenever the bundled `artoolkit5-constants` happens to carry the same literal (both
  were `0.4.0`).
- `release.yml` sets no `registry-url` and checks out no submodules (`build:wrap` never reads
  WebARKitLib). Its publish step asks npm again before `npm publish`, so "Re-run failed jobs" is safe.
- The release procedure lives in `MAINTAINERS.md`, not the README or `AGENTS.md`.
- Added, not in the plan: `.gitattributes` (`src/**` and `dist/**` LF, wasm binary), because the
  committed source maps embedded CRLF copies of `src/` that a Linux rebuild cannot reproduce;
  `npm test` in CI; a `pull_request` trigger without a branch filter, so stacked PRs get CI;
  a one-time CRLF fix for older Windows clones.
- `release-check` also verifies that every declared entry point is in the tarball, and later that
  every file listed in `files` is. The `./loader` subpath export was removed: it pointed at a
  `dist/loader.js` that no release from 0.1.2 to 0.3.0 ever shipped.

**Task 3 (scripts outside a terminal)**
- `tty` requires stdin **and** stdout to be terminals; Docker's error is about stdin.
- Step 4's `node scripts/build-wasm-docker.mjs < /dev/null` was not run: it starts the real wasm build.
- `resolveClangFormat` finds `node_modules/.bin` relative to the script, not through `createRequire`.

**Task 4 (runbook), as carried out**
- `v0.3.0` (tag and GitHub Release) was backfilled on `aba7373`, the `gitHead` npm records for 0.3.0.
- The release PR went `dev` → `main` as a merge commit; the workflow then ran once with `dry_run`
  and once for real on 2026-10-04. `0.4.0` was published with a provenance attestation.
